04隔离是怎么被「守住」的三道闸门 + 一张允许/禁止表

「不互相引用」不是靠约定，是靠三层机制同时兜：静态门禁 → 注册层过滤 → 进程层隔离。

① 静态门禁（构建前）
scripts/verify/verify-workbench-isolation.mjs
计数器 A / A' / B / C / 缺失 / M2A / A2M / K2M / K2A；规则表 EDGE_RULES:220-222。 可用 --expect M2A=0,A2M=0 把它钉成断言；--without auto 支持「临时拔掉一个模块」的验证。 manual → auto、auto → manual 的 import 必须为 0。
② 注册层过滤（运行时）
registry.ts:425-430 filterByProjectMode
所有 UI 扩展点条目都带 modes（宿主 withModes 盖入）+ 消费侧过滤；workbench 更进一步按模式键控（registry.ts:283）。 例：手写项目里，ai-chat 面板只在 ProjectLayout.tsx:217 的合池结果里（modes 含 manual）。
③ 进程层隔离（挂载）
main.tsx:44/61/89/95-97 · host.ts:216-219
按 插件 id 的 blocked() + 每个入口独立 try/catch ⇒ 一边被禁/挂载失败，另一边照常渲染。 hasModule()（moduleEntries.ts:92-94）没有任何消费点 ⇒ 不存在「看对面在不在」的分支 UI。服务端侧同样：HOST_MODE 只跳不报。
两边模块之间的引用关系（现状）
通道结论机制 / 证据
模块间静态 import禁止门禁脚本断言 M2A=0 / A2M=0；仓内只剩历史注释提及对面路径
UI 扩展点（面板/命令/路由/设置/工具栏/选区/编辑器）按模式隔离条目带 modes + filterByProjectMode；workbench 按模式键控

AI 接口（能力）可互相引用registerCapability 不盖 modes + getCapability 不做模式过滤（core 契约）
