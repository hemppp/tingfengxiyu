# AI 写作链路实测报告

> 测试时间：2026-09-12 09:00–09:083  
> 测试对象：`POST /api/plugins/autowrite/session`（多角色讨论 → 落笔 → 意图复核 → 交付）  
> 模型：`glm-5.3-flash`（OpenAI 兼容端点）  
> 结论：**主闭环可用，治理阀门真实生效；发现 2 个待修问题**

---

## 一、测试方法

新建临时账号（继承管理员 AI 配置）+ `mode: "auto"` 项目，用 Node 脚本直接消费 SSE 事件流，  
逐事件记录时间戳。测毕全量清理（账号 / 项目 / 项目独立库文件），主库恢复到测试前状态。

## 二、场景一：全新项目写第 1 章 —— ✅ 通过

**指令**：`写第1章：一个普通上班族早高峰在地铁上捡到一部还在响的手机，接起来后对方直接叫出了他的名字。`

**耗时 55.8s，9 次模型调用**，事件完整：

| 阶段 | 角色        | 产出                                        |
| -- | --------- | ----------------------------------------- |
| 讨论 | 剧情设计师     | 369 字，提出四拍结构与转折点                          |
| 讨论 | 角色设计师     | 349 字，**提出异议**：「你还有七分钟」太悬，普通上班族应先挂断再骂神经病  |
| 讨论 | 设定管家      | 345 字，查库后如实回报「四栏全是暂无，没有基准可比对」             |
| 讨论 | 剧情设计师（二次） | 281 字，**正面接受异议并给出改法**                     |
| 收敛 | 定稿官       | 523 字本章结论（节拍 / 关键物 / 伏笔 / 禁项 / 结束状态 / 待定） |
| 落笔 | 写作官       | 2145 字初稿                                  |
| 复核 | 意图复核      | **判定：打回** —— 列明 2 处实质违约                   |
| 重写 | 写作官       | 2275 字                                    |
| 复核 | 意图复核      | 判定：通过                                     |
| 交付 | —         | ✅ 《第1章》2179 字，`created: true`             |

### 亮点：意图复核不是走过场

首稿被打回，复核官指出的是**具体、可核验**的问题：

1. 正文让陈默问了「你谁？」「你到底……」，**直接违反定稿官写明的禁项**  
   「不得让陈默主动配合或追问『你是谁/什么目的』」
2. 第二通电话多报了公司楼层与地址，超出结论划定的「工位 + 衬衫」两项
3. 「七分钟」在结论中列为「待定」，正文擅自略去，未按待定项处理

并附了分条修改要求。重写后逐条销项，第二次通过。**这条链路的"讨论 → 契约 → 验收"是闭合的。**

### 亮点：设定管家没有幻觉

设定管家如实回报「库里确实没有」而非编造设定 —— 这是 2026-09-11 加「强制注入 factBlock」修复的效果，  
本次在**全新空项目**这一最易触发幻觉的场景下验证通过。

### 落库核验

- 章节写入项目独立库 `data/projects/{projectId}.db`（主库 `chapters` 为 0，符合多库设计）
- `word_count = 2179`，与正文去空白字符数**完全一致**
- 正文首尾完整，收尾落在结论要求的钩子上

## 三、场景二：重写已有正文章节 —— ✅ 治理生效

**指令**：`重写第1章：把主角陈默改成女性，名字改为林晚。`

**耗时 38.2s，7 次模型调用**，产出 2115 字初稿，意图复核一次通过，随后：

```
⛔ 交付被拦：第1章 该章已有正文，按治理原则不自动覆盖 —— 请到编辑器确认内容后再决定是否替换。
```

**覆盖保护核验结果**（对比测试前后指纹）：

| 项           | 结果               |
| ----------- | ---------------- |
| 章节 id       | 未变 ✓             |
| word_count  | 2179 → 2179 未变 ✓ |
| 正文长度        | 2275 → 2275 未变 ✓ |
| 正文开头        | 完全一致 ✓           |
| 主角是否被改成「林晚」 | **否** ✓          |
| 章节总数        | 仍为 1 ✓           |

「不自动覆盖已有正文」这条最重要的安全阀**真实生效**，且拦截信息明确交人工。  
另外本轮设定管家读到了第 1 章内容（说明 `context-resolver` 的章节栏工作正常）。

## 四、发现的问题

### P1｜讨论结论中的「落库」要求没有对应实现

定稿官与设定管家在结论中**明确要求**：「陈默、女声、那部手机三项须在本章内写实并随章落库」  
「定稿前把陈默、女声、那部手机、地铁时间线先落库，否则下一章我不认」。

实测结果 —— 交付后项目库各表行数：

```
characters: 0    foreshadows: 0    outline_nodes: 0
story_events: 0  items: 0          locations: 0
```

**结论里写了、角色也反复强调了，但代码里没有任何一步去执行。** 目前只有 `chapters` 被写入。

**影响**：下一章的讨论里，设定管家看到的仍然是「（暂无角色设定）」「（暂无伏笔）」，  
角色卡与伏笔链无法沉淀 —— 这正是本项目「灌溉水车记忆」设计要解决的问题，  
现在记忆只落了正文，没落结构化实体。

**建议**：在 `deliver` 之后增加一步「实体抽取落库」，把本章新出现的人物 / 物品 / 地点 /  
伏笔写成对应表记录（可从定稿官结论的「关键物」「伏笔」两栏结构化产出，不必额外调模型）。

### P2｜正文实际字数低于提示词要求

`ROLE_WRITER` 的 prompt 写明「篇幅 2500–4000 字」，  
`phase` 事件也向作者承诺「约 2500–4000 字」，实际产出：

- 场景一首稿 2145 字、重写后 2179 字
- 场景二 2115 字

**三次均未达到下限**（约为下限的 85%）。建议或在 prompt 里把目标字数写到中值（如「目标 3200 字，  
不少于 2500 字」），或调高 `max_tokens`，或在校验环节加一道字数检查。

### 备注（非缺陷，但值得知道）

- 直删主库 `projects` 行**不会**清理 `data/projects/{id}.db` 文件（无级联）。  
  正常路径 `deleteProject()` 里有调用 `deleteProjectDb()`，走 API 删除是干净的；  
  但任何绕过 API 的批量清理脚本都必须自己删这三个文件（`.db` / `-wal` / `-shm`），  
  且须先让 server 释放句柄（Windows 下文件被占用会 `EPERM`）。
- 本轮未测：三章滚动记忆、强制注入清单、连续多章写作、写前快照 —— 这些尚未实现或未接入。

## 五、结论

写作闭环「讨论 → 收敛契约 → 落笔 → 意图复核 → 交付」端到端可用，  
多角色讨论是**真讨论**（有异议、有回应、有收敛），治理阀门（意图门、覆盖保护）**真实生效**。

主要缺口是**记忆沉淀只做了正文、没做实体**（P1）—— 这会直接影响多章连续性，  
建议优先补上。

# 第二轮实测（2026-09-12 下午）—— P1/P2 修复验证 + 三道门接入

> 测试对象与模型同上。方法是三步走：**先验修复 → 再验多章 → 改代码后回归**。  
> 三轮都用临时账号 + `mode:'auto'` 项目，消费 SSE 事件流并直接查项目库，测毕全量清理（无孤儿）。

## 一、验证 P1/P2 修复 —— 均确认修复

### 跑 1：全新项目写第 1 章（48.1s，9 次模型调用）

| 项        | 结果                                                            |
| -------- | ------------------------------------------------------------- |
| 意图门      | **一次通过**                                                      |
| 正文       | 2504 字，**≥ 2500 下限**（P2 修复生效，未触发补写）                           |
| 交付       | 《第1章》2504 字 `created:true`                                    |
| **实体沉淀** | **`entities created=18`** —— 角色 1 / 物品 3 / 地点 4 / 伏笔 4 / 事件 6 |

落库核验（项目库）：`chapters 1 · characters 1 · items 3 · locations 4 · foreshadows 4 · story_events 6`。  
**P1 修复确认有效**（修复前这些表全为 0）。

抽取质量可接受：角色带 `role=protagonist` 与欲望/恐惧；物品带 `states`；伏笔带 `type/status/seed_chapter`。

### 跑 2：同项目续写第 2 章（65.4s）—— 暴露一个**新**问题

- **跨章记忆已通**：设定管家的发言明确引用了第 1 章沉淀的实体与伏笔  
  （「第1章伏笔也写…」「第1章四条全是 planted、未回收，第2章都不该回收」），  
  「暂无角色设定」的现象消失 —— 这是实体沉淀的真正验收标准。
- ⚠️ **但本章未交付**：意图门连续 2 次打回，3333 字正文整章作废。  
  两次打回**都卡在同一处动作细节**上（「袖口扣子是主动第三次解开、还是被蹭开」），  
  第二次改稿反而离结论更远。这暴露两个设计问题：
  1. **打回门槛过低** —— 复核官在「同一件事的表演方式」上抠字眼，而结论里并未规定写法；
  2. **打回上限后的处置是「整章丢弃」** —— 一次细节拉锯就能让一整章（约 3300 字、7 次模型调用）白跑。

→ 本轮据此改了复核官 prompt 的判定范围，并让未过门的稿子明确「已送到正文方块，可人工取用」。

## 三、回归实测（跑 3）：两章连写，136.7s

```
第1章 初稿 1384 字 → 篇幅自检触发补写 → 2888 字 → 意图门一次通过
       → 校对门 通过 → 润色门 8/10 → 交付《第1章》2888 字 → 实体 created=13
第2章 初稿 2604 字 → 意图门一次通过
       → 校对门 发现 1 处冲突 → 定向修订（rev3 2740 字）→ 仍有冲突
       → 不拦交付 → 润色门 8/10 → 交付《第2章》2740 字 → 实体 created=9 updated=3
```

**逐项对照预期，全部成立：**

1. **三道门都真跑了**：`gate` 事件 4 条（两章各 check + polish）。
2. **校对门抓到的是真冲突**：第 2 章初稿让「捡来的手机在会议室震动/响铃」，  
   而设定库里陈默「习惯开静音、连震动都关掉」—— 机判给出了出处并触发了定向修订。
3. **校对门不阻塞交付**：定向修订后仍有 1 处冲突，照常交付并提示人工确认  
   （这正是本轮刻意的设计取向：宁可带一处标注，也不要整章作废）。
4. **上一章全文注入生效**：第 2 章设定管家引用了**第 1 章的正文细节**  
   （「手机是第七节车厢专座上捡的」「结尾停在站台柱子边没接也没走」）——  
   只靠摘要做不到这一点；写作官的第 2 章开头也是接着上一章结尾那一刻写的。
5. **意图门不再抠细节**：两章都一次通过（对比跑 2 的两次打回）。
6. **实体跨章累积**：第 2 章 `updated=3` —— 命中了第 1 章沉淀的既有实体并补章号/状态。
7. **篇幅自检真的用上了**：第 1 章初稿只有 1384 字（模型波动），补写后 2888 字。

## 四、仍然存在 / 未验证

- 水车记忆（三斗 + 三层时间戳）、连续多章自动续写、正文流式落点、台账回放 —— **本轮未做**。
- 校对门/润色门的成本：每章 **+2 次模型调用**（冲突时 +3）。可接受，但值得记一笔。
- 复核官与校对官偶有**结论分歧**（复核说「禁项没被碰」，校对说「与设定冲突」）——  
  两者视角不同（契约 vs 设定库），不是 bug，但同时为 false 时会让人困惑，尚未处理。
- 旧批次流水线（`server/autowrite/*`、FlowStore、`/batches`）仍在仓库里，仅加了废弃标注；  
  **是否物理删除**属待决项（见 handover §8-1）。
