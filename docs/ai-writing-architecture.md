# AI 写作框架 · 完整架构设计

> 状态：设计定稿，实施进行中（第 1 批已落地，见 §9）。
> 本文件把「双框架分流 / 三栏工作台 / 智能体阵容 / 三道门 / 灌溉水车记忆」织成一套自洽架构。
> 所有设计都标注了**落到哪个文件或接口**，不是空想。

---

## 0. 一句话

**手写与 AI 写作是两个互斥模块**：手写是人执笔、AI 打辅助；AI 写作是**一组设计智能体先讨论出结论、写作官据此写、同一批智能体再复核**，记忆用**固定斗数的水车**循环承载。

## 1. 双框架分流

`Project.mode: 'manual' | 'auto'` —— 创建书籍时用滑动开关二选一，**两套 UI 完全互斥**。

| | 手写（manual） | AI 写作（auto） |
|---|---|---|
| 界面 | 罗盘气泡 + 自由浮窗面板 | 三栏固定工作台 |
| 面板 | 12 个（角色/地点/物品/伏笔/地图/时间线/大纲/笔记/统计/关系图/参考书/导出） | 一个都不挂载 |
| AI 角色 | 对话助手（8 个技能可选） | 编排器 + 四智能体 |
| 技能 | **不含 `auto-write`**（按 mode 过滤） | —— |

- 落地：`packages/shared` 的 `ProjectMode`；`ProjectLayout` 按 mode 早返回分流。
- autowrite 插件**不再注册手写侧的「自动写作」浮窗面板**（`registerProjectPanel` 已移除），
  只保留 `registerChatRail`（属对话本身）与 `registerSkillIcons`（技能内容归插件）。
- **数据是同一份**：章节 / 角色 / 时间线两套框架共用，差别只在 UI。切换模式不迁移数据。

## 2. 工作台（三栏常驻）

```
┌──────────────┬────────────────────────┬──────────────┐
│ 左：智能体对话 │  中：世界状态仪表盘      │  右：正文     │
│  · 交流流      │   计划 / 最近变动 / 伏笔 │  宣纸信笺     │
│  · 用户输入框  │   物品 / 角色 / 地点     │  (流式落点)   │
├──────────────┴────────────────────────┴──────────────┤
│ 底：花名册（规划/写作/校对/润色）+ 批次总控              │
└───────────────────────────────────────────────────────┘
```

- **左右两栏可拖宽窄、可各自收起**；中间有 340px 最小宽度保护。
- 中栏不是给正文的：AI 写作时人最关心的是**世界变了什么**（变动流水、伏笔是否回收）
  和**接下来写什么**（批次计划），正文退居右栏。
- 落地：`apps/web/src/components/layout/AutoWriteWorkbench.tsx`（壳）、
  `WorldStateBoard.tsx`（中栏仪表盘）、`WorkbenchPlan.tsx`（计划卡，拉 `GET /api/plugins/autowrite/batches`）。

## 3. 智能体阵容

| 角色 | 职责 | 是否查库 |
|---|---|---|
| **剧情设计师** | 本章发生什么：冲突 / 转折 / 钩子 | 否 |
| **角色设计师** | 人物动机、状态、关系，与上一章是否接得上 | 否 |
| **设定管家** | 对照设定库与时间线拦冲突、挑伏笔时机 | **是（唯一必须读库的）** |
| **写作官** | **只读结论**写正文，不参与争论 | 是（按需取原文） |
| **用户** | 随时插话，可推翻任一方案 | —— |

**设计要点**

1. 讨论**必须是来回的** —— 三个 agent 各写一份报告并列，那是三份文档，不是交流。
2. **写作官不参与讨论** —— 避免被过程中被否决的方案带偏。
3. **设定管家必须查库**，不能凭记忆 —— 它拦的每一条都应有出处。

## 4. 主流程

```
用户提需求
  → 设计讨论（剧情 / 角色 / 设定，来回 1–2 轮）
  → 收敛：本章结论
  → 写作官写初稿
  → 意图复核（同一批设计智能体，各对照自己在结论里的条目）
      ├─ 有不符合 → 打回（带结构化问题清单）→ 重写 → 再复核（上限 2 次）
      └─ 全过 ↓
  → 校对硬门（对设定库一致性）
  → 润色软门（节奏 / 文笔评分）
  → 交付（写章节 + 打快照）
```

### 4.1 「本章结论」是契约

讨论的产物不是聊天记录，是一份**可比对的清单**：

```
节拍：扑空（钥匙开门／空匣／新灰）→ 自我说服破产 → 追查 → 被掐断
关键物：空匣内壁新划痕（埋，第 5 章用）；半枚湿脚印 + 一缕头发（指向熟人）
伏笔：密信本体不动，第 4 章再动
禁项：不得回收密信；不得出现来者正面
结束状态：她知道"有人比她先到，且认识她"，但不追出去
```

没有这份清单，意图复核就无从对照，打回也只能瞎猜。

### 4.2 打回必须带修改指令

反例：「不符合，重写」。
正例：

```
打回第 1 次
· 剧情设计师：结尾写成她自行离开，结论要的是「被外力掐断」 ——
  改为门外传来脚步声，她没看清就退出去，不必出现人物。
· 角色设计师：自我说服只占第 3 段一句，扩写为前半章主线，至少 400 字；
  触发点用「新灰」：她先否认，再被手心的灰逼醒。
· 设定管家：补一句「空匣内壁有道新划痕」，别解释。
其余保留，不必重写全章。
```

**能局部改就不整章重写** —— 省 token，也不容易把对的地方改坏。

### 4.3 收敛由用户拍板

不交给某个 agent 宣布「就这样定了」。实践中用户的一句话（「划痕留着，脚印加头发」）
往往是最有决定性的输入。

## 5. 三道门（别搞混）

| 门 | 审什么 | 形态 | 归属 |
|---|---|---|---|
| **意图门** | 写出来的是不是我们商量的那一章 | 点 —— 清单验收 | 三个设计智能体 |
| **校对门** | 全文与设定库有没有矛盾 | 面 —— 全文扫描 | 校对官（已有 `check_draft`） |
| **润色门** | 文笔 / 节奏 | 评分 | 评审官（已有 `polish_draft`） |

- **意图门放最前** —— 它防的是「白写了」，最贵的浪费。方向错了整章作废，事实错误可以后补。
- 意图门与校对门的边界：**「答应的事做了吗」 vs 「有没有说错话」**。
- 建议：三个设计智能体在**同一轮**里各审自己那一维，产出**一份合并的打回清单**，
  否则写作官要被打回三次。

## 6. 记忆架构：灌溉水车

> **2026-09-13 更新（口径已修正）**：本节的水车**不是一层共享记忆**，而是**每个智能体各自**的
> 「记忆迭代方式」—— 实现在 L2（一 agent 一台），斗位落在 `agent_memory`。
> 完整两级分层（L1 只有权威事实 / L2 各智能体独立记忆）、闸门与审计、角色权限矩阵见
> **`docs/multi-agent-memory-architecture.md`**（§1.0 讲清了两者的区别）。

以**灌溉水车**为原型 —— 关键不是"会动"，是**斗数固定 + 循环复用**。

```
   舀入（一章定稿交付）
        ↓
   [ 斗1 Ch4 ][ 斗2 Ch3 ][ 斗3 Ch2 ]  → 倒出（最老一斗出界）
        ↑ 每来一章，整体右移一格
        ↓
   压成一句话梗概 → 蓄水池（长期库，原文不丢）
```

| 水车 | 记忆 |
|---|---|
| 固定的斗数 | 工作记忆容量**恒定**（3 斗 = 3 章） |
| 低处舀水 | 新章定稿 → 正文进工作记忆 |
| 高处倒水 | 最老一章出界 → 压成一句话梗概 |
| 蓄水池 | 长期库 —— **倒掉不等于丢**，按章号随时取回 |
| 持续旋转 | 循环复用，不无限增长 |

### 6.1 三层时间戳

| 层 | 例 | 用途 |
|---|---|---|
| `chapterNo` | 4 | **逻辑时间** —— 排序、引用「Ch3 那桶水」 |
| `ingestedAt` | 10:24 | **真实时间** —— 新鲜度与审计 |
| `storyTime` | 第 3 日 | **故事内时间** —— 判断「她说'昨天'对不对」 |

`storyTime` 最容易被漏、但在小说里最要命：**章节号与故事时间不是一回事** ——
一章可能写三天，也可能一天写五章。没有它，agent 只能按「上上章」推断时序，跳跃叙事必错。

**附加好处**：水车是循环的，所以**斗位序号本身就是相对时间戳** ——
斗 1 永远最新、斗 3 永远最老，agent 引用时天然带新鲜度。

### 6.2 规则

- **舀**：只在**一章定稿交付**时。写作中的半成品不占斗位，否则记忆被草稿污染。
- **倒**：斗满且有新水才倒；最老一斗压成**一句话**梗概（不是摘要），原文留在蓄水池。
- **钉**：关键转折章「沉底」不参与旋转。**倾向不做** —— 转折的后果本该由设定库承载
  （角色状态、物品变更、伏笔），靠钉住旧章节保记忆等于绕开设定库。

## 7. 上下文装配：常驻 + 强制注入 + 按需读取

**只靠"让 agent 自己去读"防不住污染** —— agent 不知道自己不知道什么，不会主动去查
「第 1 章的伞是不是坏的」。所以必须区分三类：

| 类别 | 内容 | 机制 |
|---|---|---|
| **常驻** | 最近 3 章全文（水斗）+ 全书一句话梗概 + 本批次细纲 | 自动装配，体量恒定 |
| **强制注入** | 上一章全文、本章细纲、出场角色卡、未回收伏笔、已确立硬设定 | 不注入必然写错，不能交给自主判断 |
| **按需读取** | 更早的情节细节、次要角色历史 | `read_chapter` / `search_all` / `get_settings`，**带章号来源返回** |

**一句话**：常驻靠「骨架 + 强制注入」保命，长尾靠「按需读取」省预算。缺一，要么写错，要么爆上下文。

## 10. 未决项

1. **阵容增删** —— 是否加「节奏医生」（管篇幅与张力曲线）或「对话打磨」？
2. **写作官看什么** —— 纯结论，还是结论 + 讨论摘要（保留语感上下文）？
3. **收敛是否每次都等用户点头** —— 倾向：无冲突自动收敛，有冲突才停。
4. **水车的「钉」** —— 要不要给关键转折章留例外通道？倾向不做。
5. **多代理的实现层级** —— 继续前端切分（轻，但"交流"是表象），
   还是后端真跑多角色（重，但讨论可留痕、可复现）？**这一条决定 B/C 的做法。**
